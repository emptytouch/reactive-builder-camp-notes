## 关键概念

**源链 / 目标链**
- 一个 Reactive 合约能订阅多条源链的事件，也能往多条目标链发回调，目标链还能在 Solidity 里按条件选。
- 主网必须配主网，测试网必须配测试网，不能混用。
- 测试网：Reactive 侧固定 **Lasna（5318007）**；目标链 **Ethereum Sepolia 11155111 / Base Sepolia 84532 / Unichain Sepolia 1301**。
- 回调靠 Callback Proxy 验真：`msg.sender` 必须是该链代理，且原始发起方是 Reactive Signer。同一个代理地址会出现在不同链上（如 `0x476F…3585` 既是主网 Robinhood 又是 Base Sepolia），所以校验必须连 chainId 一起认。

**三个数（今天真正的核心）**

| 概念 | 我的理解 |
|---|---|
| 源链（Origin） | 出事的链，Reactive 从它读事件日志 |
| 目标链（Destination） | 回调落地的链，状态在这改 |
| balance 余额 | 合约自己账上的钱，只有合约主动交出去才能抵债 |
| reserves 预付 | 存在系统合约里的信用额度，扣费最先消耗它 |
| debt 欠款 | 已欠未付，**>0 就停摆** |
| 停止执行的条件 | 有欠款即停，跟 balance 多少无关 |

- 记账规则两条：收费**先吃 reserves，吃完才产生 debt**；存款**先清 debt，剩下的才进 reserves**。→ 合约不可能同时有 reserves 和 debt。
- 债务检查在所有 gas 消耗之前，所以是**静默停摆**，不报错，你只会发现「没反应」。
- Reactscan 上看 `active` / `inactive`；欠债发 `BlacklistContract`，清零发 `WhitelistContract`；同一笔交易里被 `pay()` 结清的根本不会进黑名单。

**费用公式**

- `fee = p_base · C · (g_used + K)`；`p_base = max(tx.gasprice, block.basefee)`，`C = _gasPriceCoeffPer1000()/1000`，`K = _extraGas()`。
- Reactive 侧默认：C = 1000（1 倍）、K = 100,000 gas、pay 预算 `_maxChargeGas` = 50,000。**callback 侧没有默认值**，各代理自己配，必须去代理合约查。
- **K 是固定底噪**：每次触发白挂 10 万 gas；订阅越宽触发越频繁，这笔底噪被乘几千次。→ 这才是「订阅要加 `_limit`」的经济原因，不是代码风格。
- gas 上限：Reactive 交易最大 900,000；callback 最低 100,000，低于此值**直接被忽略**（连失败都不算）；代理还要先扣 `_extraGas` 和 `_maxChargeGas`，剩下才转发，不够就 `InsufficientGas`。

**充钱两条路**

- `depositTo(合约地址)` → 进系统合约的 reserves，自动抵扣，推荐默认用，也是救活别人负债合约的唯一办法。
- 直接转账 → 只加 balance，合约得自己 `pay()` / `coverDebt()` 才能抵债；没暴露 `coverDebt()` 的话钱**困在合约里**。
- 直接往系统合约转 REACT 会记到**发送者自己地址**，不算给合约充值。

**失败不退款**

- `react()` revert → 记 `ReactiveContractReverted`，全额收费；callback 失败 → 记 `CallbackFailure`，全额收费，都不退。
- 唯一例外：回调打向没有代码的地址，收费前被拒。
- 结论：宁可提前 `return` 少烧 gas，也不要 revert。

**两侧币种不同**：Reactive 侧付 REACT；callback 侧付目标链原生币（ETH / BNB …），不是 REACT。


执行环境：`/d/Web3/reactive-builder-camp/starter`，`source .env` 后执行；Lasna RPC `https://lasna-rpc.rnk.dev/`，系统合约 `0x8888…8888`。

| 参数 | 实测值（2026-11-18 00:28） | 解读 |
|---|---|---|
| `_gasPriceCoeffPer1000` | **1000** | 除以 1000 = `C = 1`，即无额外倍率 |
| `_extraGas` | **100000** | `K = 100,000 gas`，每次 `react()` 的固定底噪 |
| `_maxChargeGas` | **50000** | `pay()` 的 gas 预算上限，**不进费用公式** |

**结论**：Lasna 当前配置就是官方初始值，没有被改过。所以公式可具体写成：

```
fee = p_base × 1 × (g_used + 100000)
```

以 Lasna gas price 100 gwei、一笔简单 `react()` 为例，约 0.015 lREACT（官方速查表的实测值）。这意味着订阅范围越宽、触发越频繁，那 10 万 gas 底噪会被乘上很多次——所以订阅必须加次数上限。**注意 `_maxChargeGas` 的 50k 不参与计费，它只是系统合约调用 `pay()` 时的 gas 预算；自定义 `pay()` 写太胖会 `PaymentFailure`。**

## 自测复盘（自己先答，再对照）

1. balance 有 5 REACT、debt 0.001 → `react()` 还调吗？
   答对：不调。但表述要改准确——不是「调用了没反应」，而是**系统合约压根不会调用 `react()`**、回调代理也不会投递；这是主动停服务，不是静默失败。
   补一个关键点：那 5 REACT 的 **balance 救不了它**，因为 balance 必须由合约主动交给系统合约才能抵债。正确救法：`depositTo(合约地址)`（钱进 reserves，先清 debt 再进 reserves），或合约暴露了 `coverDebt()` 就用它。注意一旦已进 debt 状态，`pay()` 的自动结算路径也不成立——它只在「发生收费时」被调用，而停摆状态下根本不会有收费。
2. 直接往系统合约转 1 REACT，为什么合约还是 inactive？
   答错。不是「不能被手动使用」，而是**这笔钱记账记在发送者（我的 EOA）名下，根本没记到合约账上**。系统合约按地址记账，我合约名下的 reserves 仍是 0。必须 `depositTo(目标合约)`。
3. 一次 `react()` 什么都不做就 revert，省钱吗？
   答对：不省，revert 照样全额收费。补充：还会记 `ReactiveContractReverted` 事件；想省钱应该提前 `return` 少烧 gas；唯一不收钱的情况是回调打向没有代码的地址（收费前就被拒）。
